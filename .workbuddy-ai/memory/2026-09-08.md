# 2026-09-08

## Search-driven discovery: find businesses without supplying URLs

User's core ask: "find businesses just by searching the name, niche, category,
etc and it should automatically search the internet for the required info
without me having to input urls".

### What was built

- **`src/lib/discovery/`** (new module)
  - `types.ts` — `BusinessDescriptor`, `SearchResult`, `DiscoveryCandidate`,
    `DiscoveryOutcome`, `SearchProvider` contract.
  - `providers/brave.ts`, `serper.ts`, `tavily.ts`, `searxng.ts` — real APIs,
    auto-enabled by `BRAVE_SEARCH_API_KEY` / `SERPER_API_KEY` /
    `TAVILY_API_KEY` / `SEARXNG_URL`.
  - `providers/duckduckgo.ts`, `providers/bing.ts` — zero-key scraped
    fallbacks, last resort only.
  - `query.ts` — `buildQueries` (max 3 variants, quotes known names).
  - `ranking.ts` — `classifyResult` (directory/social/reference/news),
    `registrableDomain` (multi-part TLDs), `isRelevant` relevance gate,
    `rankCandidates`.
  - `index.ts` — `discoverBusinessUrls`, `providerStatus`, `labelForProvider`,
    automatic provider failover.
- **`src/lib/scraper/resolve-target.ts`** (new) — the single place that turns a
  draft into seed URLs. Both storage backends now share it.
- **Job creation**: new `targetType: "search"` (added to Prisma `TargetType`
  + migration `20260906010000_add_search_target_type`). `/api/scraper/jobs`
  now resolves descriptors into real URLs and returns 422 when nothing is
  found instead of creating an empty job.
- **`/api/scraper/discover`** (new) — preview search results before creating
  a job; UI lets the operator tick which websites to crawl.
- **Wizard UI**: `target-step.tsx` rewritten — "Web search" is now the default
  target type with name/niche/category/location/keywords fields, a live
  "Find websites" preview and checkboxes.

### Bugs found and fixed

- `domainToUrl("ftp://example.com")` produced `https://ftp/` — same class of
  bug as the earlier `normalizeUrl` one. Now rejects any non-http scheme and
  any host without a dot.
- Domain jobs were created with **zero** queue URLs in
  `/api/scraper/jobs` (only `url-list` built a queue). Fixed by centralising
  in `resolve-target.ts`.

### Hard-won findings about free search (important)

Measured live from this machine:

- DuckDuckGo `html.duckduckgo.com/html/` works, but returns **HTTP 202 with a
  bot challenge** after a handful of queries. Detect and report it.
- **Bing silently degrades**: "emergency plumbing Manchester" returned
  dictionary definitions of "emergency"; "accountant Leeds" returned French job
  ads; "Northwind Traders" returned Microsoft login pages. It does not error —
  it answers a different query. This is why it is last-resort with a strict
  relevance gate in front of it.
- Mojeek serves a captcha page (HTTP 200, `<title>Captcha</title>`).
- Public SearXNG instances: mostly 429/403 or JSON disabled.
- Brave HTML `search.brave.com` → 429.
- OSM/Overpass: works but **UK coverage is effectively zero** (0 plumbers in
  Manchester; 4 in Manchester NH). Not viable as a source.
- Nominatim: returns almost no `website` tags.

**Conclusion**: zero-key scraping is not dependable. Recommend a real API key
(Brave free tier). Documented in `.env.example`.

### Relevance gate (deliberate design)

`rankCandidates` defaults to `relevance: "all"` — every dimension the operator
filled in (name / trade / location) must appear in URL+title+snippet. Company
names match in full; trade and location match on a 5-char stem. There is
deliberately **no** loosening fallback: returning plausible-but-wrong websites
is worse than returning none. Blank dimensions never reject.

### Gotchas

- A mocked `Response` body can only be read once; when a mocked `fetch` is
  shared by several providers, use `mockImplementation(() => new Response(...))`
  not `mockResolvedValue(new Response(...))`.
- `.next/dev/types/validator.ts` can be left corrupt by a killed dev server and
  then breaks `tsc --noEmit`; delete `.next/dev` to regenerate.
